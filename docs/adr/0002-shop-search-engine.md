# ADR 0002：校园门店搜索引擎

- 状态：Accepted（采用 MySQL 基线，暂不引入 Elasticsearch）
- 日期：2026-10-09
- 范围：Phase 4B 新增门店搜索入口，不替换旧列表或详情缓存

## 背景与决策

搜索用例需要名称关键词、类别、价格区间、最低评分和距离。MySQL `tb_shop` 是门店事实来源。当前没有真实数据规模、目标负载、查询延迟或相关性评测证据证明 MySQL 无法承担这些用例；也没有明确的中文分词、纠错或复杂相关性需求。

因此先交付 `GET /shop/search` 的 MySQL 基线，不添加 ES 依赖、服务、索引或同步事件。名称采用经过字面转义的 LIKE 子串查询；固定筛选、排序和 Haversine 球面距离在数据库执行。每次搜索直接读取数据库，COUNT 与本页数据在同一个只读 REPEATABLE_READ 事务内，不依赖详情 Redis 缓存或旧 GEO 预热。

这不是“MySQL 永远足够”的结论，也不是“ES 没用”。它是当前需求与已知证据下减少运维面、避免无理由双写一致性成本的选择。尚未进行实际压测。

## 方案比较

| 方案 | 收益 | 成本与限制 | 当前决定 |
| --- | --- | --- | --- |
| MySQL LIKE + 固定筛选/距离 | 复用事实数据，提交后的新事务可读到数据，无额外索引同步窗口 | `%关键词%` 与距离表达式可能扫描大量候选行，精确 COUNT 也有成本；不提供分词、纠错或相关性排序 | 作为可验证基线 |
| MySQL FULLTEXT | 仍在一个数据库内，支持全文检索能力 | Token、停用词和 ngram 语义与子串不同；中文搜索质量与配置需要专门语料评测，不能作为透明替换 | 有明确全文需求后评估 |
| Elasticsearch | 丰富的全文分析、相关性与地理检索能力，搜索资源可独立管理 | 新增部署、Mapping、数据初始化、增量事件、重试、删除、重建/切换及运维；索引存在最终一致性窗口 | 暂不引入 |

## 基线限制

- 关键词只匹配名称，遵循现有 `utf8mb4_general_ci` 排序规则；不是分词、全文或拼写纠错。
- V005 的类别/价格与评分索引是候选索引，不保证所有排序走索引；NULL-last、混合排序、LIKE 和 Haversine 均可能触发扫描/filesort。
- 单请求 COUNT/本页快照一致不意味着多次翻页冻结在同一版本。并发修改后下一页仍可能移动；后续可依据用例评估游标与版本策略。
- 球面直线距离不是椭球测地距离或步行/驾车路线。半径和页深限制只是工作量约束，不是性能 SLA。
- 每条查询配置 5 秒 JDBC statement timeout，不包含连接池排队、建立连接、事务开始/提交和整个 HTTP 请求的时间，也不保证所有网络故障均在 5 秒内完成。
- 没有新增搜索缓存、Redis GEO 同步或 CDC。旧 `/shop/of/name`、`/shop/of/type` 保留旧实现边界。

## 重新选型条件

满足任一条件时开启新的评估阶段，而不是自动安装 ES：

1. 明确要求中文分词、拼写纠错、词权重或相关性排序，并给出代表性语料与可重复的搜索质量评价方法。
2. 在约定的目标数据量、查询分布和并发负载下，保存原始 SQL/执行计划、资源使用与延迟结果；合理索引、查询和分页优化后仍不能满足事先定义的目标。
3. 明确需要独立搜索资源、复杂地理/聚合查询，且收益足以覆盖数据同步、额外服务及运维成本。

若以学习为主要目的引入 ES，应明确标注学习目标，不宣称当前规模必须使用 ES。若决定引入，必须在同一完整阶段交付版本化 Mapping、历史初始化、提交后的可靠增量同步、幂等/乱序与删除处理、失败重试、可观察积压、全量重建及别名切换/回滚，并用实际故障证明恢复链路。不能先装依赖再把一致性工作留空。
