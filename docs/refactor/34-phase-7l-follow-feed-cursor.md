# Phase 7L：关注 Feed 同分值游标累计

日期：2026-10-14。基线 `4b30965a70b0ab3863a4ecead17c0df7fddf01ff`。只修关注Feed读取中的同时间组偏移，不增加可靠投递、MQ、新路由或DDL。

## 失败复现与根因

旧 `queryBlogOfFollow(max,offset)` 用 Redis `reverseRangeByScoreWithScores(key,0,max,offset,2)` 取原批次，返回最小时间minTime和本页末尾同时间条数；但同一时间组跨页时未累计输入offset。生产代码未修改时，新单元测试6项中2项失败：输入max=1000/offset=2、返回两条score=1000，期望nextOffset=4却得到2；输入offset=6只剩一条同score，期望7却得到1。后续请求于是可能重复读旧批次，不能从旧代码宣称静态Feed无重复分页。

按系统化调试先恢复临时专用Maven缓存中缺失的原版本公开依赖POM，再确认真正的业务失败；Luna测试中的Redis API导入/参数与同分值降序fixture也核对修正。没有更改项目依赖、个人设置或共享Redis来掩盖失败。

## 修复与接口契约

仍为 `GET /blog/of/follow?lastId=<正Long>&offset=<非负Integer>`，lastId传入服务max，offset默认0。每批最多2个原始Redis成员，按score降序、同score成员字典序降序，随后由数据库加载可见动态并保留原批次顺序。

- 当本页最小score与传入max相同，nextOffset = 输入offset + 原批次末尾同score成员数。
- 当本页已进入更早score，nextOffset = 原批次末尾同score成员数，不能带上较新score的旧offset。
- 游标依据Redis原成员，不能改用DB可见行数量。撤回/缺失动态过滤后 `list=[]` 仍有minTime/offset，客户端继续用该游标请求；不补齐、不移除Redis成员。
- Redis无原成员时仍返回 `Result.ok()`，无data；这是本阶段保持的终止形状，不能把过滤空列表误当终止。
- 响应 `{list,minTime,offset}` 类型不变；累加恰好达到Integer.MAX_VALUE可表示，超过则在数据库查询前抛 `OPERATION_FAILED`（422），不返回溢出或倒退的游标。此守卫用模拟极值批次验证，不声称真实构造过数十亿Feed成员。

例：静态7条score=1000依次返回偏移2、4、6、7，末页1条，随后无data；3条score=2000、4条score=1000时，四页游标依次为(2000,2)、(1000,1)、(1000,3)、(1000,4)。读请求不写动态、Redis成员或分数。

## 保证范围和兼容

仅在原始ZSet成员/score跨请求保持不变、合法整数毫秒时间score的情况下，验证选定连续分页能按Redis顺序完成，不重复、不漏原批次。DB可见性与正文不是冻结快照，撤回仍可过滤行。同分值成员是字典序而非数值ID排序，score不是提交次序，不能据此推导发布顺序或全局时间一致性。

跨页新增、删除或重评分会改变rank偏移，仍可能重复/遗漏；不新增冻结快照、复合ID游标、重建/补投/消费重试。已有投递非原子和Redis点赞两步一致性不在本阶段。未验证任意损坏成员、非整数/非正score、缺失作者资料等旧故障路径；未进行实际压测，也不把分页修复宣称为性能优化或可靠Feed系统。

无schema/迁移/API目录数量变化：V001–V010、48个映射/13个Controller、BlogController10条不变。既有客户端可以继续用同形状游标，但部署后建议从新分页会话（offset=0）开始；已由旧错误逻辑产生的offset不能自动重建。回退到仍理解V010撤回标记的7K版本不撤销数据但会重新带回分页缺陷；7J及更旧忽略撤回标记，仍不可直接回退。
