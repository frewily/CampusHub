## 实际运行与拒绝记录

按系统化调试流程，先读取实际失败证据、补失败测试，再作最小修复；没有放宽计数、身份、耗时或库存门槛。

1. 官方固定附件下载因速度较慢超过 120 s，续传成功后仍校验原定 archive/binary SHA-256。只下载进程使用已实际确认可达的本机代理；负载与初始化 HTTP 不走代理，没有全局安装或修改 shell 配置。
2. 第一次 `--run` 在第一次预热发出抢购请求前失败：SQL/Redis helper 返回字符串，数值门禁拒绝文本 `"0"`。增加边界专用 `cli_integer`，仅接受规范非负十进制，保留 JSON 数值指标的严格类型检查。
3. 第二次 `--run` 的预热 HTTP 检查通过，但 Redis 6.2.24 的 redis-cli 明确拒绝 `--json`。使用仅白名单读取 HGETALL/SMEMBERS/XRANGE/XINFO GROUPS 的 Lua cjson 包装，保留嵌套数组和字符串 Long ID；不升级 Redis、不改变业务 Lua，不在负载中执行证据命令。
4. 第三次完整六正式/六预热均对账成功，但发布门禁将 k6 的空 root_group 固定 MD5 当作疑似 32 位凭据拒绝。第四次仍因白名单误设空数组而拒绝：原生导出实际是空对象。读取真实字段后补回归，只允许该固定路径、固定值及精确空 root_group 结构；其他字段相同值或随机 32 位值仍拒绝，JSON 解码后的隐私字段也检查。
5. 最后一次在新项目从头执行完整六正式/六预热，全部门禁、精确清理与发布成功。仅该次结果进入公开目录；前四次结果留在私有诊断，各次测试资源均由 finally 精确清理，不挑选旧轮、不删慢轮、不改原始导出。

以上失败是本轮测试驱动/CLI/隐私解析问题，不作为已证实的业务缺陷或性能优化收益。第三/第四次业务批次通过但没有发布，也不混入正式统计。
