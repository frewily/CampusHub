# Phase 7K：动态作者逻辑撤回

日期：2026-10-13。基线 `6c5f24ffdcb50c2e687f3ed75b6525d2d346a553`。在作者编辑后补最小撤回用例，不物理删除动态或教学数据；原教学目录保持只读。

## 契约和保留边界

新增 `DELETE /blog/{id}`（`withdrawBlog`），正 Java Long，无必需 body，成功 `Result.ok()` 无 data。仅 USER/MERCHANT/ADMIN 可调用，三角色均仅存量作者本人，ADMIN 不覆盖；匿名、停用、无角色/未知角色为401，他人为403，缺失为404，非法ID为400。作者从会话取，不接受客户端指定。事务内先当前读行锁，核对归属后只将 `withdrawn` 从0改为1；影响行数非1为422，数据访问异常为无cause的通用500。重复本人撤回成功且不执行UPDATE、不刷新update_time；撤回后的他人请求仍为403。

V010 增加 `tb_blog.withdrawn TINYINT UNSIGNED NOT NULL DEFAULT 0`。历史行默认可见，新发布强制0；内部字段不暴露于 Blog JSON。撤回只改标记及数据库自动update_time，保留标题/正文/图片、作者/门店、create_time、点赞/评论计数、全部评论/回复状态和原文、审核审计、Redis点赞与Feed成员/分数；不清图片文件，不回填历史计数。

## 各入口的可见性

| 入口 | 新请求看到的撤回后语义 |
|---|---|
| 详情、点赞名单、编辑、点赞/取消点赞 | 404，包括作者本人；没有回收站/撤回后编辑/恢复 |
| 热门、本人、用户动态列表 | 过滤撤回行，正常分页；Blog实体 `@TableLogic(0,1)` 使生成的SELECT/count/UPDATE含可见性条件 |
| 关注Feed | Redis原批次仍推进游标，数据库读取过滤撤回行；可能返回 `list=[]`，保留原批次minTime/offset，不自动补齐 |
| 一级评论/回复列表、创建 | 404；创建使用动态当前行锁的可见条件，不沿用旧RR快照判断 |
| 已有本人一级评论/回复撤回、管理员隐藏 | 仍可操作原有行，沿用动态先锁、评论后锁；各自改变评论状态/计数，不恢复动态 |
| ADMIN单条/按动态审核记录 | 保留查询，不join当前可见动态、评论或操作人 |

自定义SQL不受 `@TableLogic` 自动保护，因此显式补编辑SELECT/UPDATE、评论普通读取/新增行锁及计数递增条件。已有评论撤回/隐藏仍锁保留动态（不加可见条件）；审核读取保持不变。点赞先锁可见动态，再访问既有Redis路径，避免撤回已提交后开始的新点赞修改Redis。

## 并发与故障语义

撤回、编辑、评论创建与点赞沿同一个动态行锁串行。撤回先提交后，等待的编辑/新增评论/点赞当前读应拒绝；新增互动先完成可被保留。重复撤回的当前读能看到已提交标记。锁是单库事务顺序，不是版本冲突检测、DB/Redis原子性、可靠Feed投递或全局读屏障。此前已经开始的读取可能仍返回其已读到的旧内容，不能撤销已经返回或客户端缓存的内容。外部图片地址仍可能可读；逻辑撤回不等于隐私擦除。

点赞依然是DB计数和Redis两步操作，Feed仍有旧投递/同分数分页问题；本阶段不承诺这些全链一致性。5秒XML语句timeout不是SLA，未新增可见性索引，也未进行实际压测。

## 部署与回退

新库bootstrap按schema→V001…V010→合成seed。现有库必须先备份、审查已知结构并人工应用V010，再升级应用；已有卷重启不会自动迁移。按列名重复跳过，不自动核验或修复同名错误列定义，不能替代生产迁移评审。缺少标记列时新应用的生成查询会失败，不可先升级应用。

旧应用忽略撤回标记并可能重新展示内容，**不能直接回退到7J或更旧版本**。需要修复发布或使用同样理解标记的兼容版本；不要DROP列、重置标记或物理删除动态来回退。保留状态/数据比“可随意回退”重要。

应用目录48条映射、13个Controller，BlogController10条；评论Controller6条、ADMIN评论Controller3条不变。范围不含动态审核/恢复、编辑历史、通知、举报、前端、可靠Feed及物理擦除。
