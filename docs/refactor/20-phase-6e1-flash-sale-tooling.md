# Phase 6E1：限量活动负载工具与验收门禁

日期：2026-10-10。实现基线：`aa86770b01a8fcc32df1dbf0ede0c414334787b4`。

6D 对照原文发现限量活动实际压测仍未完成，用户同意继续这一方向。本阶段先固定模型并交付工具，正式测量/结果发布是下一小阶段 6E2；不增加业务或改运行架构。

## 范围

- `scripts/load/flash-sale.js`：一人一个 VU、有限两请求，严格受理/原 ID 重放/SOLD_OUT 检查，固定指标标签；私有 HTTP 身份见证。
- `scripts/run-flash-sale-baseline.py`：复用既有隔离 Compose/固定资源/原生工具原语，合成身份与活动、账本核对、单调时钟后台完成观察、原始导出/哈希/清理/发布门禁；显式区分 `--inspect-only` 与 `--run`。
- Python 离线门禁与 Node VM HTTP stub 回归，以及[负载方案](../performance/flash-sale-plan.md)。

正式模型为 20/200 不同合成账号，库存各为账号数的一半，每人连续两次请求，每组合三轮；每轮有独立 10 账号/5 库存的预热。计划中六批正式 HTTP 共 1320 请求、330 首次受理/330 重放/660 售罄；这些是门禁的预期数量，**不是实测结果**。

没有 Java/Lua/schema、权限、业务重试、正常部署或历史 6C 原始结果变化。不做实际 Docker 抢购负载、不提供活动延迟或 TPS 数据，不将观测收敛时间伪装成逐单异步落库延迟。

## 安全与事实边界

host 固定 localhost，port 仅由驱动创建的资源发现；初始化 HTTP 不使用代理且禁重定向。合成身份由本测试自己的 DB/Redis fixture 建立，真实过滤器仍校验角色/账号；不是发送短信或真实注册。fixture/log 仅私有临时目录，public 汇总不发布见证/ID/凭据。

静态追到当前认证过滤器仅接收原始 token，不解析 Bearer；初稿脚本的 Bearer 头由系统化调试定位后修正，并由本地 VM 回归验证。额外增加 HTTP 见证与 Redis/DB 全映射的核对，防止“订单数量对但响应 ID 错”被接受；缺失/重复证据、奇数 Redis pairs、错误状态、负计时、失败归档/积压和未经清理均拒绝发布。

`--run` 路线在本阶段只有静态/离线证据；真实 native HTTP/Redis CLI JSON/Compose 账本/资源清理仍待 6E2 验证。现有支持脚本曾在其他阶段运行通过，不等于新组合流程已完成网络验收。
