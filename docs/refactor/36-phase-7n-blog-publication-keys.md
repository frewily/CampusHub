# Phase 7N：可选发布请求编号与安全重试

日期：2026-10-15。基线 `01bd83c885c3d27bc45f16bae83bb909baac8f4e`。只补 `POST /blog` 的可选客户端发布幂等，不新增业务路由、后台查询、清理任务、消息中间件或性能目标。

## 复现与范围

按系统化调试先在未改生产代码的 HTTP 安全夹具复现：同一有效身份、内容和 `Idempotency-Key` 连续请求，模拟发布服务依次返回31/32，第二次预期31却得到32。旧 Controller 没有读取该头，也没有成功请求账本；这证明编号被忽略、重复进入发布服务，不把模拟依赖当作真实数据库重复落库证据。后续以真实 MySQL 事务和 Compose HTTP 另验新契约。

7M的 Feed 重放幂等不等于客户端发布幂等。这里选择保留旧无编号路径，只有主动提供编号的请求使用新服务；不是自动识别一切相似内容，也不是禁止用户再次发布相同内容。

本阶段初稿的两请求IT通过，但四请求HTTP验收出现500；随后自建MySQL四调用复现，SQLSTATE40001/1213指向重放 `FOR UPDATE`，只分类输出的引擎状态确认账本死锁。重复INSERT持有共享记录锁，再多人升级独占锁形成竞争环。改为不可变收据的 `FOR SHARE` 共享当前读后，四调用与旧RR快照两个回归同轮通过，死锁分类为false；未把500改成允许通过，也未增加盲目无限重试。诊断实例不提供performance_schema状态行，因此使用私有实例引擎状态仅分类，不输出原始SQL/记录转储。

完整Compose也暴露7K遗留冻结分页夹具未等待7M投递完成的时序：后台会把手工3000/2000/1000重评分恢复成发布分数，导致预期非终止页变成无data。用三个明确阻塞的合成收件意图受控复现恢复原分数，再等全部确认后才安装冻结分页分数；只改测试前置条件，投递业务语义不变。

## 请求协议

仍是三角色允许的 `POST /blog`、原DTO、字段白名单和200 `Result.ok(blogId)`；响应仍为数字 Long ID，不新增响应字段或复用缓存的HTTP响应。身份每次都先经过现有会话、ACTIVE账号和有效角色校验，编号不是登录凭证。

- 不带 `Idempotency-Key` 时仍走原发布服务，每次都可能产生新动态，不能承诺重试不重复。
- 提供时，只允许一个头值，应用看到的值必须完整匹配 `[A-Za-z0-9_-]{1,64}`，大小写敏感；空/逗号/非ASCII/应用层空白值或多值为400，不默默退回无编号路径。应用不自行trim；HTTP连接器可能按协议移除外侧空白，不承诺网络字节级验证。应使用不含业务内容或个人信息的随机编号。
- 作用域是 `(当前用户ID, 编号)`，不是角色、会话token或全站编号。不同用户可用同编号；同用户换编号仍会新建，不能把编号当内容去重键。
- 同作用域、相同有效创建内容重试，返回首次成功提交的原ID，不再保存动态、读取新受众或登记/快速尝试Feed投递。变化的有效内容为409 `CONFLICT`，不覆盖原记录。
- 失败回滚不占用编号；响应丢失/网络断连后客户端必须保留原编号及原有效内容重试。SQL锁等待或依赖错误可能返回通用500；有限语句timeout不是请求SLA，不能据此保证每次并发调用都200。

## 指纹与事务

`BlogPublicationService` 先校验用户、编号和原DTO约束，用 `ApiModelMapper` 得到白名单动态，再计算创建请求指纹。指纹固定域 `CampusHub:POST/blog:v1`，按shopId、title、images、content顺序进行长度前缀SHA-256：nullable shopId用固定哨兵，字符串以Java UTF-16代码单元和长度编码，避免简单分隔符歧义或异常Unicode替换造成等价。它不是签名、认证、隐私匿名化或无碰撞数学保证；变更v1规则须有兼容设计。

无图的省略/null/空串/trim空白已归一为空串，所以相同编号视为同请求；非空图片、标题、正文不做额外trim、大小写或Unicode归一。JSON字段顺序及被忽略的id/userId/计数等不参与指纹。DTO原始长度/关联图片约束仍须通过，即使它看起来能归一成已有请求也不能跳过校验。

服务通过Spring事务代理调用，复用7M实际可写事务与同步门禁，首条SQL之前拒绝未代理/只读调用。V012 `tb_blog_publication_request` 普通INSERT占位，然后在同一InnoDB事务里调用原发布服务保存动态/收件意图，最后条件UPDATE记录原ID；完成必须影响1行，否则422并整体回滚。SQL异常转换为无cause通用500；代码不主动输出编号、指纹、原文、SQL或异常文本，不是对任意日志配置的安全承诺。

唯一主键让同用户/编号的并发INSERT等待竞争者提交或回滚。只在占位INSERT处捕获 `DuplicateKeyException`；MyBatis/InnoDB该语句失败后使用 `SELECT ... FOR SHARE` 共享当前读检查已提交的指纹/ID，避免旧RR快照隐藏胜者。重复INSERT已经持有共享记录锁，多个重复请求再申请独占读锁会有升级死锁；成功账本不可变，重放不需要独占锁。不能把此策略照搬为JPA/任意数据库的事务保证。其他死锁/数据库错误仍不当作成功重放。缺失/无效完成ID的异常历史账本行报通用500，不自动抢占、删除或再发一条。

## 历史语义、部署与回退

账本是原成功创建的ID收据，不是正文历史或当前可见性。动态被编辑、撤回甚至外部删除后，同原请求重试仍只返回原ID，不恢复内容/状态；详情继续按当前数据返回，撤回仍404。若希望新发一条，必须显式换编号。重放不重新投递，不意味着当前Redis一定还有Feed成员。

表按用户和ASCII大小写敏感编号建主键，保存请求摘要、完成ID及UTC创建时间；无外键级联、TTL、自动清理或旧动态回填。成功账本持续保留，存储成本随不同编号增长；容量治理、过期协议、批量清理和数据恢复另定范围。手动删账本会失去对应幂等保证，不能伪装成无损清理。

新库bootstrap schema→V001…V012→seed。已有库先备份、核对InnoDB结构并人工审查应用V012，再升级；现有卷重启不自动迁移。`CREATE TABLE IF NOT EXISTS`只保留同名表，不修复错误形状/排序规则。不新增配置开关；无编号路径仍只需已有7M结构，但新版有编号路径必须具备V012。

回退7M等旧应用会忽略编号，保留表也不能继续承诺发布幂等；必须先停止依赖该协议的发布/自动重试，安排兼容入口或采用修复发布。不得删账本/待办来制造回退完成。7J及更旧不理解V010撤回标记，仍不可直接回退。没有HA、跨库事务、全Feed重建、跨页冻结、浏览器/CORS接入或实际压测结论。

API仍48条应用映射/13个Controller，BlogController10条；Java8、Boot2.7.18、MyBatis-Plus3.4.3和Maven3.9.9不变。
