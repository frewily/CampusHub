# 动态发布成功，不等于所有人立即收到

实现与证据见[Phase7M](../refactor/35-phase-7m-blog-feed-delivery.md)。这是AI辅助完成的学习材料，不是本人已独立掌握的证明。

旧链路先提交动态，再逐个ZADD。如果第二步失败，用户收到失败却已经有动态；盲目重发可能多出一条。只给Redis循环加重试不能记录进程退出后还欠谁，直接把Redis调用放在数据库事务里也不能让Redis一起回滚。

现在动态与“本次投给谁、用哪个固定分数”同事务保存。提交前不写Feed；提交后快速尝试最多32个目标，不在仍绑定的JDBC连接上确认待办；后台每批32个到期目标恢复并确认。事务回滚不触发提交回调。

事务门禁要放在发布首条SQL之前，不能只在入队时检查，否则未经过代理的内部调用可能已经保存动态。门禁不会自动开启事务；正常路径要经过Spring代理，模拟ThreadLocal标记的单测也不能代替真实事务验收。

收件人来自当次DB关注查询，重试不重新查询关系；取消关注后，本次已保存的意图仍会处理。它不是全局提交时订阅快照，也不等于之后新关注者会收到历史动态。撤回不删待办，读取端仍过滤原内容。

为什么重试用旧score？ZSet成员相同可防止第二个成员，但如果每次都用当前时间，旧动态会被重试推到顶部。固定score既用于Redis重放，也参与DB条件确认；Redis返回false表示已有成员也已确认，null不能确认写入。

Redis成功后DB确认失败会留下待办，再次ZADD同成员/同score。允许两个worker重复处理，因为副作用可重放、失败更新不重建已删除的意图；不据此宣称恰好一次、跨系统事务或HA。失败记录只有异常类名，没有异常文本、SQL、内容或凭据。

客户端POST没有幂等键，丢响应后重发仍可能建立新动态；后台投递幂等和前台发布幂等是两回事。确认后意图会删除，之后Redis丢失数据也没有自动历史重建。认证阶段仍需要Redis，不能把提交后故障恢复说成全Redis停机仍可发布。

部署先应用V011再升级，保留待办不能DROP来回退。默认启用后台，暂停轮询不代表积压已消失。复述时请自己演示原失败、第二意图插入回滚、Redis故障保留、ACK失败重放不改分数，以及为什么本次验收不是压测、硬杀或生产证明。
