# 单条回复隐藏审计：历史记录不是当前状态

后续7Q已增加[按动态游标分页](reply-hide-audit-pagination.md)及V014索引；下文“不做分页、没有新DDL”保留7P当时范围，不是当前整个项目边界。

## 实际开发照着走

只补一个读取用例：管理员按replyId查询7O留下的隐藏审计。先确定哪些字段可以返回，再实现只读查询，分别验证身份、字段白名单、缺失、历史保留和事务快照。不要顺手扩成全部审核后台。

可以使用这个Prompt：

> 阅读已有回复隐藏写流程和V013，只实现ADMIN单条回复隐藏审计读取。响应仅九个元数据字段，五个ID为字符串；不join当前内容或账号，不写任何行。先保留旧路由缺失的失败证据，再分别做mock权限测试、真实MySQL快照测试和隔离HTTP验收。报告证据边界后再提交审查。

继续条件：源码、机器目录和接口表一致；真实查询不修改状态/计数，不能读到未提交的审计；合法管理员可以读取保留记录。阶段结果见[7P记录](../refactor/38-phase-7p-reply-audit-query.md)，测试通过不等于本人已掌握。

## 查询什么

```http
GET /admin/blog-comments/replies/9007199254740995/hide-audit
authorization: <当前有效管理员会话>
```

这是示意，不提供读取共享账号、验证码或会话的方法。只有当前有效ADMIN能读取；回复作者或当时执行隐藏的人，如果现在不是ADMIN也不能读取。

成功 `data` 只有九字段：`id`、`replyId`、`blogId`、`rootCommentId`、`operatorUserId`、`reason`、`fromStatus`、`toStatus`、`createTime`。前五个用字符串，避免JavaScript数字超过安全整数范围后丢失精度。返回DTO而非评论Entity，不带正文、昵称、当前可见性、liked或计数。

## 为什么不先查回复是否存在

审计回答的是“系统保留了哪次状态转换的元数据”，不是“回复现在是否隐藏”。V013已有回复、动态、根、操作人ID和原因，查询它不需要当前业务行参与。

如果后来有人在数据库外部移除了回复、根、动态或原操作人，只要审计仍保留且当前调用者是有效ADMIN，原记录仍可读。这不是本阶段增加了删除功能；测试中的删除仅发生在自建数据库的合成行。

反过来，旧回复的status=2也不证明7O曾成功执行；没有V013记录就是404，不补造历史。审计表不是内容快照，也不是防数据库管理员篡改的日志。

## 为什么用普通SELECT

7O写操作需要锁定当前读来复核资格；7P只读历史记录，不抢写锁，使用只读REPEATABLE READ事务和普通参数化SELECT。

写事务已经INSERT但尚未提交时，另一个读取事务不应看见该审计，也不应等待写方提交才能报告缺失；写方回滚后仍没有这条历史。写方提交后，新事务才可能看到它。如果读方早已建立RR快照，即使写方后来提交，同一旧快照仍可404。这不是“审计丢失”，而是快照语义；重新发起新请求进入新事务才能刷新。

只读注解和5秒语句超时不是性能或生产SLA。单元测试可以核验注解/参数/XML；只有通过事务代理、真实MySQL与受控并发，才能验证本机数据库行为，仍不能外推所有数据库或线上负载。

## 两类记录不要混用

根评论的V008审计仍由原单条/按动态分页接口读取。回复的V013只由这个新单条接口读取。不能把replyId塞进根接口、返回改名的commentId，或悄悄让原分页混入另一类记录；那会改变旧客户端理解的对象。

7P没有新表或索引，依赖7O已审查应用的V013。已有卷重启不会自动迁移，同名错表不会因 `CREATE TABLE IF NOT EXISTS` 被修复。回退7O会失去新读取入口，但应保留审计、状态与计数；不要删除历史来制造回退成功。

本阶段不做回复审计分页、导出、恢复、举报、通知、历史回填、任意状态修复或生产迁移。
