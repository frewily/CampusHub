# 动态作者编辑：完整替换、行锁与边界

## 为什么用完整替换

`PUT /blog/{id}` 表示客户端提交新的完整内容：`title`、`images`、`content` 一起描述编辑后的动态。它不是“只改我传来的几个字段”的 PATCH。调用方应先拿到当前内容，再提交希望保存的完整版本；这样 `images: null` 等输入的含义不会因为字段省略而变得含糊。

请求 DTO 只接收这三个内容字段。作者、门店关联、计数和时间不是客户端可编辑内容。即使 JSON 带有 `userId`、`shopId` 或 `liked`，这些未知属性也不能被复制进数据库更新对象。

## 为什么不全 Entity 更新

动态 Entity 还包含作者、门店关联、点赞数和评论数等字段。若把请求拼成一个部分填充的 Entity，再调用全字段更新，遗漏字段可能被写成 null/default，或者把读取时的旧计数覆盖掉。编辑 SQL 因此应只更新 `title`、`images`、`content`；作者、关联和互动计数由数据库原有状态继续管理。

这也解释了为什么请求的 `shopId` 不用于决定图片校验：服务端先锁定并读取存量行，再从那一行取得不可变的 `shop_id`。门店关联动态编辑后仍须有非空白图片；无关联动态可以没有图，并将 null、空串或 trim 后空白归一为 `""`。合法非空图片字符串保留原样。

## 为什么要锁定存量行

事务里的 `SELECT ... FOR UPDATE` 是当前读，会等待同一动态上正在进行的编辑事务，并在锁取得后以存量行核对作者、门店关联及内容。这样授权和更新都针对同一条受锁记录，而不是先用旧快照判断、稍后再无条件写入。

编辑之间会被行锁串行化，但这不是乐观并发冲突检测。两个作者本人编辑先后成功时，后一个事务仍可覆盖前一个事务的内容。没有版本号、If-Match、历史版本或编辑审计，客户端若需要避免基于旧副本覆盖新内容，当前契约没有提供该保证。

若三个内容字段与锁定行完全相同，可以直接成功而不发 UPDATE。除了减少无意义写入，这还避免数据库自动更新时间字段因 no-op 请求而刷新。发生写入时也只改三个内容字段，不顺便触碰 `createTime` 或互动计数。

## 读写之外的边界

本阶段不删除旧图片文件，不重投或重排 Feed，也不改变评论、审计或 Redis。Feed 的旧读取方式可能先取动态 ID、再从数据库加载内容，因此之后的新读取能看到已提交的新正文；但投递仍不是可靠队列，先前已经返回给客户端的结果也不会被回写，跨请求没有冻结快照。

5 秒 SQL timeout 是单条语句的保护设置，不是接口延迟 SLA。无 schema 迁移也只表示结构不变，不证明生产安全。本轮 83 项定向、398 项默认统计（4 设计跳过）、60 项显式 MySQL IT、28 组目标 Compose 通过；真实更新后返回零行的守卫已验证整体回滚，独立连接在提交前读取旧版本、提交后读取新版本。默认套件不发现 *IT；HTTP mock、实际 MySQL 和真实 HTTP/Redis 的证据分别记录，不混为全部端点或生产验收。
