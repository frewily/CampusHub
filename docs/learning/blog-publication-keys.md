# 发布重试：用原请求编号找回原动态ID

实现与证据见[Phase7N](../refactor/36-phase-7n-blog-publication-keys.md)。这是AI辅助工程与学习材料，不自动证明本人已独立掌握。

7M记录了“内容已经提交、Feed还欠谁”，但客户端不知道成功结果时再POST仍会多一条。对Feed做幂等，不能替代发布本身的幂等。

现在客户端可为一次逻辑创建生成一个 `Idempotency-Key`，未知结果后仍用原编号/原内容重试。同用户、同编号、同有效创建内容找到原ID；换了内容则409，而不是覆盖原动态。用户故意发第二条时用新编号；没有编号的旧客户端行为保持兼容。

不能先查一下“有没有编号”再新建：两个线程都可能查不到。也不能先单独提交一个占位、或先提交动态再单独记编号：会留下卡住编号或重复动态的窗口。这里用数据库唯一主键竞争占位，账本完成、动态和Feed意图处于同一事务，失败全部回滚。

竞争失败后为何用 `FOR SHARE`？普通RR一致性读可能沿用一个早于对方提交的快照；唯一键已经冲突，不等于普通SELECT马上能读到对方。重复INSERT已持共享记录锁，多人再升级独占读取会死锁；已提交收据不可变，重放只需共享当前读，再比摘要和原ID。本轮四请求验收暴露了独占读的死锁，实际MySQL复现后修正；不能只用两请求或mock推断并发正确，也不能把MyBatis方案套到JPA。

摘要不是随便拼字符串或对原始JSON直接hash：字段顺序、未知字段和无图归一应保持等价，标题/正文真实变化不能合并。实现固定v1域和长度前缀，逐Java UTF-16代码单元编码，测试须覆盖字段边界和Unicode。摘要不是密码学签名，也不提供隐私匿名化。

返回原ID不代表重建原内容。编辑/撤回后重试原创建请求，只拿到原ID，当前内容不恢复；账号停用或身份失效仍先401。账本不缓存认证、全文或HTTP响应，不能绕过每次身份校验。

成功账本不自动过期；删除账本就可能让同编号再次创建。V012先迁移再升级，回退旧应用会忽略编号，不能只保留表就承诺旧版本也幂等。暂停重试/兼容入口或修复发布需要单独安排。

请独立复现：旧入口忽略编号、同编号并发只提交一条、不同内容409、账本完成失败时全部回滚、失败后原编号可再次成功，以及为什么这些验收仍不是生产容量或HA证明。
