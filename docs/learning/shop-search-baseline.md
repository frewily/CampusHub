# 门店搜索：先把 MySQL 基线说明白

## 当前实现解决什么问题

新入口 `GET /shop/search` 把名称子串、类别、价格、评分和距离组合为一条可验证的搜索用例。调用链是 `ShopSearchController → ShopSearchService → ShopSearchMapper.xml → tb_shop`。数据库是事实来源；不读取详情缓存，也不等待旧 Redis GEO 集合更新。旧列表路由仍在，不等于旧列表已经采用这套实现。

## 为什么区分 Request、Criteria 与 Response

Request 只允许公开参数；Controller 的 binder 再限制可绑定字段，防止内部 SQL 模式、offset 或实体写字段进入用例。Bean Validation 限制页深、页大小和排序，并检查价格上下限、成对且有限的坐标。Service 再次验证，保护非 HTTP 调用。

Criteria 是验证后产生的不可变查询投影：trim 关键词，构造 LIKE 模式，算出有上限的 offset。Response 只含可公开的门店字段与分页信息，64 位 id/typeId 使用字符串，避免 JavaScript 数字精度损失。不要为了“分层”复制实体的所有内部字段。

## 关键词不是把百分号直接传给 LIKE

用户输入 `%` 应搜索名字含百分号的门店，不应匹配全表；`_` 也应是普通字符。选择 `!` 为显式 escape，依次把 `! → !!`、`% → !%`、`_ → !_`，最后在两侧加 `%`。SQL 使用 `LIKE #{q.likeKeyword} ESCAPE '!'`，反斜杠作为普通文字。

所有值用参数绑定。ORDER BY 不能直接绑定列名，因此先严格校验 sort，再由 XML `<choose>` 输出固定 SQL 分支；没有 `${}`。值转义解决 LIKE 的通配符语义，参数绑定解决 SQL 数据/语法边界，这是两件不同的事。

名称匹配遵循旧表的 `utf8mb4_general_ci`，不是逐字节比较。不提供中文分词、相关性或纠错；要增加这些能力，先定义代表性语料和评价标准。

## 为什么 COUNT 与本页放在同一个事务

单独 COUNT 后另开一个连接查询页面，并发提交可能使 total 与 items 基于不同版本。只读 REPEATABLE_READ 事务让这两条普通 SELECT 使用同一个 InnoDB 一致性快照。所有排序追加 `id ASC`，同价格/评分/距离不会因缺少确定性 tie-break 而随机重排，NULL 价格/评分显式放最后。

真实 MySQL IT 安装 Spring 事务拦截器，用 latch 在 COUNT 后暂停，然后在另一个连接提交新行；同次搜索仍返回旧快照，下一次搜索看到新行。裸 `new ShopSearchService(...)` 没有事务代理，不能拿它证明快照一致。

这只能保证一次请求内一致。分页请求之间数据可能变化，OFFSET 仍可能出现移动；后续可以评估游标，但复杂价格/距离排序也要定义稳定的游标字段和更新语义。`hasNext` 来自 `page * size < total`，不是“页面正好填满就一定有下一页”。

## 距离与成本

Haversine 使用平均地球半径 6371008.8 米。计算值夹紧到 [0,1]，避免对跖点附近浮点误差使反三角函数非法。距离是球面直线距离，不是导航路线。支持经纬度查询源点边界与负值，不代表已经迁移旧表 UNSIGNED 坐标写模型。

有坐标但不按距离过滤/排序时，坏存储坐标只使距离为 NULL，不丢弃该门店；距离排序或半径筛选必须排除坏坐标。真实 IT 用合成坐标覆盖原点、半径附近、反日界线、极点与对跖点，不把它称为真实地理数据迁移验收。

V005 是候选索引：类别/价格/id 与评分/id。前导 `%` LIKE、距离函数、NULL-last 与混合排序不保证能利用它们，不能写“增加索引就优化了搜索”。先在真实数据量和代表性查询上记录 EXPLAIN，再压测延迟与数据库资源。必要时先增加地理候选范围再算精确距离，但范围跨日界线和极点时也需要验证，当前没有这项优化。

最大 size 50、page 500、radius 50000 米和两条 SQL 各 5 秒 statement timeout 是未调优限制，不是 HTTP 延迟 SLA。精确 COUNT 仍可能昂贵，连接池与事务时间也不在 statement timeout 内。

## 故障与 ES 取舍

Mapper 的数据访问异常转换为 `SHOP_STATE_UNAVAILABLE`。事务开始/结束在服务方法之外，Controller 的局部异常处理覆盖 transaction/data-access 异常，输出相同503且不带后端异常文本。失败不是“没有门店”。没有设置搜索缓存，也就没有新增 MySQL/ES 双写窗口。

服务端只记录固定故障事件与异常类名，提供安全分类，不打印可能包含SQL/参数/连接信息的驱动异常原文或堆栈。测试捕获日志检查分类与脱敏。它不等于完整根因追踪；后续可观测性阶段再设计安全诊断、指标与告警，不能为排障便利把敏感数据写入日志。

当前不引入 ES，因为还没有规模/负载/相关性证据要求它。引入后必须承担历史初始化、增量同步、幂等和乱序、删除、重试、重建、切换及回滚，而不是仅增加一个查询客户端。详见 [ADR 0002](../adr/0002-shop-search-engine.md)。

## 面试追问

1. 参数绑定能否代替 LIKE 通配符转义？不能，绑定不会改变 `%` 的匹配语义。
2. REPEATABLE_READ 是否解决整个翻页过程的变化？不能，当前每个 HTTP 请求是一个独立快照。
3. 为什么有索引仍可能 filesort/扫描？过滤、表达式与排序顺序不一定匹配索引，子串与距离计算也不是普通 B-tree 等值访问。
4. 为什么不用 Redis GEO？它需要更新/初始化链路；当前搜索以数据库提交事实为准，旧 GEO 不是自动同步的搜索索引。
5. 为什么不加 ES？当前基线可满足功能用例，尚未证明性能或相关性不足；重新选型需要需求与实测，不是技术栈数量。
6. 做过什么性能优化？本阶段没有实际压测和提升数字，只交付功能基线、候选索引、工作量约束与正确性验收。
