# 关注 Feed：偏移属于哪个时间组

实现与验证见[Phase7L](../refactor/34-phase-7l-follow-feed-cursor.md)。这是AI辅助重构的学习材料，测试和提交不自动证明本人掌握。

Redis按score倒序读关注Feed，每批2条。同毫秒多个成员时还按成员字典序倒序，不能想当然按ID数值排序。请求lastId是包含边界的最大score，offset是在这个范围内已经跳过的成员数。

如果一页末尾仍处于请求时间组，之前跳过的同组成员仍在范围内，必须累计offset。7条同时间成员四页的nextOffset是2、4、6、7；每次只返回本页数2，会让下一请求再次读相同批次。

进入较早时间组后，请求范围将缩小；较新组已不在新范围里，旧offset不能再加。3条较新、4条较旧的四页游标应为 `(2000,2)→(1000,1)→(1000,3)→(1000,4)`。先数原批次末尾同score条数，再决定累计还是重置。

DB过滤掉已撤回动态时，空 `list` 不等于Redis到尾。游标从原批次取得，所以应继续请求；只在Redis无原成员、返回无data成功时终止。一次读取不删除Feed成员、不补齐列表，也不重新投递。

这个方案依赖跨页ZSet不变。插入同score新成员、删成员或改score都会改变rank；因此修正累计不是跨页快照或exactly-once方案。7L当时没有新增投递outbox；后续[7M](../refactor/35-phase-7m-blog-feed-delivery.md)补发布意图和固定分数故障恢复，但仍没有全Redis丢失重建、历史补投或冻结分页。数据库原文/可见性仍逐请求变化，前一页数据不会被撤回追溯取消。

请求offset与响应offset仍为Integer；无法表示的累加会失败，而不是溢出成负数或倒退。极值模拟测试不等于数十亿成员负载测试，合法Java Long成员往返也不等于前端JSON大整数已验证。

接管学习时，请自己复现修复前的两个失败，说明为什么跨时间组要重置、为什么过滤空页仍要前进、为什么同score的排序不是数值ID排序，以及什么时候仍会重复或漏项。
