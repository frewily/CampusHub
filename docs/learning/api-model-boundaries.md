# API 模型边界：字段白名单与兼容取舍

## 为什么不能直接把请求绑定到 Entity

`Shop` 中的 `score/sold`、`Blog` 中的 `id/userId/liked`、`Voucher` 中的 `type/status` 并不属于同一个可写权限范围。直接接受整个实体时，客户端可以提交这些字段；即使通过角色校验，也不意味着有权修改实体中的每一个属性。

Phase 2D 采用请求模型字段白名单，并通过显式 `ApiModelMapper` 设置实体。实体后来新增列时，不会自动成为 HTTP 可写字段。

## 边界如何协作

1. JSON 绑定：请求只保留允许的业务字段，冗余字段忽略。
2. Bean Validation：检查请求是否完整、数值与长度是否合法。
3. 方法授权：检查当前身份是否可以操作目标商户或门店。
4. 显式映射：初始化服务端计数、类型和状态；不复制主键、作者或时间戳。
5. Service：保留资源授权、事务与持久化逻辑，作者从当前登录身份获取。

校验通过不代表授权通过。商户提供一个格式正确的其他门店 ID，仍然应该返回 403。字段白名单也不能替代服务层归属检查。

## 为什么创建与更新不共用一套门店请求

创建必须提供完整门店资料；更新允许只提供 `id` 和要改的字段。创建可以指定商户归属，通用更新不能转移归属。两个请求模型虽然重复少量业务字段，但能直接表达不同约束，不需要依赖字段复制或复杂的校验分组。

普通券与限量活动则共享同一组券面信息，因此 `FlashSaleCreateRequest` 继承 `VoucherCreateRequest`，仅追加库存和时间校验。没有为每个用例重复建立 Request、DTO、VO、Entity 四套对象。

## 为什么用显式映射

批量 `copyProperties` 依赖同名字段。一旦模型或实体发生扩展，可能无意复制不该写入的字段。当前字段数量较少，逐字段映射的维护成本可控，新增可写字段需要明确修改映射。代价是增加字段时要同时维护请求、映射和测试。

## 为什么冗余字段忽略而不是拒绝

旧客户端可能回传读取时拿到的完整实体。忽略冗余字段可以保留合法业务字段的兼容性，同时阻止统计值、作者和主键进入服务。代价是客户端不一定马上发现误传字段；调用方应按阶段接口记录发送字段。若未来切换为严格拒绝未知字段，应作为明确的接口契约变化发布。

用户资料响应则使用独立对象，避免为隐藏时间戳而修改数据库查询得到的原实体，也避免后续新增持久化列自动暴露到 API。

- 角色有门店写权限，为什么还需要限制可写字段？

- 如何证明动态作者、计数、主键和活动类型不能被客户端伪造？
- 为什么映射使用白名单？实体新增一个列会影响 HTTP 契约吗？
