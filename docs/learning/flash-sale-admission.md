# 限量活动受理：设计取舍

抢购 HTTP 请求同步等待 Redis 规则核验与事件写入，成功返回的 ID 是预生成订单 ID。数据库订单由已有 Stream 消费者异步处理，因此 `ACCEPTED` 不是最终订单状态。下一阶段需要可查询的状态和失败补偿。

一人一活动的原订单 ID 保存在 `seckill:request:{id}`，已有 `seckill:order:{id}` 继续表示参与。脚本先查原 ID，后查库存和时间，这样已受理用户在售罄或活动结束后仍能取回原 ID；资格仍须有效。历史 Set 记录没有原 ID 时返回冲突，不凭空生成新订单。绝对 TTL 固定到结束后 24 小时，重试不会延长保留期；过期后不保证原 ID 可取回。

Lua 在 Redis 单实例上按顺序执行，但运行错误不自动回滚。预检 key 类型、严格校验数据，并把可能失败的 `XADD` 放在扣库存前，降低“事件没写、库存已扣”的风险。仍须承认进程故障、Redis 持久化和跨系统一致性风险；跨槽 Redis Cluster 也不能直接运行这组多 key 脚本。

先写数据库，提交后才发布 Redis；这样数据库回滚不会留下可抢的活动。但提交后的 Redis 失败无法回滚数据库。初始化脚本拒绝覆盖任一已有活动 key，防止重置剩余库存或去重记录。应由运维或后续恢复流程核查数据库和 Redis，再决定如何安全修复，不自动重试创建接口。

账号状态、角色及活动状态来自数据库与当前认证上下文，是受理前的快照；Lua 再核验 Redis 中的活动时间与状态。两个存储没有跨系统锁或事务，状态恰在请求中变化时仍可能有短暂不一致。若未来要求严格即时撤销，需明确管理状态传播与并发边界，并用真实端到端测试证明。

面试时须说明：保留数字 ID 和原 Stream 字段是为渐进兼容；JS 客户端读取超过安全整数范围的 ID 仍有精度风险。Redis 成功不等于 MySQL 下单成功。当前数据库没有可证明的学生认证字段或名单，不能宣称实现学生资格校验。并发正确性测试不能产生 QPS、P95 等性能指标；尚未进行实际压测。
