# 直接回复隐藏：锁、当前读、独立审计与计数

Phase 7O 给管理员增加了隐藏一条直接回复的入口：

```http
POST /admin/blog-comments/replies/{replyId}/hide
Content-Type: application/json

{"reason":"违反社区规则"}
```

它只处理一层直接回复：`parent_id` 必须大于0，`answer_id` 必须等于 `parent_id`。管理员只能通过ADMIN角色操作，回复作者是谁不影响审核权限。请求复用已有隐藏DTO，reason不能全空白，长度最多255个Java UTF-16单元；操作人从当前登录身份取得。成功是200 `Result.ok()`，不带data。

## 为什么按这个顺序加锁

数据库行锁需要先知道要锁哪条动态和根评论。服务先校验replyId、reason和会话操作人正ID，再检查事务门禁；确认实际事务及同步已激活、且事务非只读后，才执行第一条SQL（候选读取也在门禁之后）。然后读取候选回复，取出动态ID和根ID；这个普通读取只是定位线索，不能当作最终资格判断。接着按固定顺序锁动态、锁规范一级根评论、最后锁目标回复，并在每次锁定读取时重新确认归属和关系。

```text
参数/reason/操作人校验
  → actual transaction + synchronization active + writable 门禁
  → 候选回复（只定位）
  → 锁动态
  → 锁同动态的一级根评论（parent_id=answer_id=0）
  → 锁并复核目标直接回复（parent_id>0, answer_id=parent_id）
  → 改状态、扣计数、写专用审计
```

固定锁序让会改同一组评论数据的操作按一致顺序竞争，降低交错锁导致的风险。根评论必须存在且属于同一动态，但根的可见状态不作为阻挡条件：根已隐藏或被作者撤回，仍可以单独处理一条关系合法的回复。动态作者撤回后也一样，前提是相关行还存在、目标回复本身仍符合规则。

InnoDB的普通读取在REPEATABLE READ事务中可能继续看旧快照。`SELECT ... FOR UPDATE` 是锁定当前读，会读取等待锁期间已提交的新版本。因此前置候选只回答“去哪找”；拿到锁后的当前读才回答“现在还能不能执行”。本阶段的显式竞态测试用 `TransactionTemplate` 建立RR旧快照；winner独立提交后，普通audit count仍为0，hide路径的当前读仍成功。

事务门禁发生在参数、请求和正操作人校验之后、任何SQL之前（包括候选查询）。它检查实际事务已激活、事务同步已激活、事务非只读。这样即使有人绕过Spring事务代理直接调用服务，也不会先查询或执行一半SQL再发现没有事务保护。

## 状态变化与重试

第一次成功隐藏时，回复从0变成2；同一事务还会把动态的 `comments` 计数按零下限减一，并向V013插入一条审计。三个写入都必须恰好影响一行，否则整体回滚、返回422。数据库访问异常映射成不带底层原因的通用500。

重试时不能只看 `status=2`。旧系统或其他流程可能早已把回复设为2，但并没有本功能的审计。只有V013里存在同一回复、动态、根，以及 `from_status=0,to_status=2` 的匹配记录，才说明7O已经成功处理过；这种重试返回200，不再次更新、不再扣数，也不覆盖第一次的操作人和原因。status=2却没有匹配审计仍然404。1、3、NULL和不合法关系也不接受。

隐藏后回复状态是2，作者的撤回入口只接受自己的0/3状态，所以作者不能撤回这条已隐藏回复。系统保留原文、liked、回复与根的关系、根评论及兄弟回复；不删除、不级联，也不改变其他回复状态。

## 两类审计表不能混用

V008 `tb_blog_comment_hide_audit` 为一级根评论隐藏服务，7G单条读取和7H按动态分页只读它。V013 `tb_blog_reply_hide_audit` 为直接回复隐藏服务，以 `reply_id` 唯一，一条回复最多有一条本用途记录。两种对象有各自的状态变更记录，因此根评论审计查询不会自动包含回复审核记录；7O也没有新增读取或导出路由。

V013保存回复ID、动态ID、根评论ID、操作人、原因、from/to状态和创建时间。它没有外键，不复制评论正文，不自动过期，不回填过去已经是status=2的回复。数据库管理员仍可直接改数据，审计表不是防篡改日志。

## 计数是什么意思

`tb_blog.comments` 是历史写入维护的派生计数。隐藏一条可计数回复时减一；遇到NULL或0时按零下限处理。这只能避免减成负数，不能修复旧数据或漏记的历史变化。

它也不等于“当前还看得见多少条评论”。例如根评论隐藏后，其下回复可能仍保留；回复被隐藏后，根和兄弟也都还在。要知道某个列表当前显示多少内容，应查询该列表的可见性规则，不能把聚合计数当作实时可见行数。7O不扫描历史行、不回填，也不重算总数。

## 部署和证据边界

新库的迁移顺序到V013。已有库应先备份并核对表结构，再审查V013后升级应用。`CREATE TABLE IF NOT EXISTS`不会修复同名但定义错误的表。回退旧应用不能删审计、把status改回去或手工补计数来模拟回滚；7K引入动态withdrawn标记，7J及更早版本不识别它，仍不能直接回退。

本阶段最初的HTTP mock请求在路由尚未加入时预期200、实得404，只说明当时没有这个handler。它不触达MySQL，不能证明事务、锁、计数或审计行为。阶段真实IT与最终验证状态以[7O阶段记录](../refactor/37-phase-7o-direct-reply-moderation.md)为准；不外推未覆盖的生产或容量结论。
