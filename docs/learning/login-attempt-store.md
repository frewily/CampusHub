# 登录策略和Redis机制分开看

7AG把登录验证码消费和失败计数的存储操作放到 `LoginAttemptStore` 后面。服务决定何时拒绝、何时记失败、何时查账号和签发会话；Redis适配器决定使用哪个key、哪个Lua、如何传参数。端口不把Redis key暴露给服务，适配器也不把null或未知结果“翻译”为成功。

## 沿一条请求复述

合法手机号 → 读失败计数并按原Long规则解析 → 已到5次直接拒绝 → 消费验证码 → 查找/创建账号并检查ACTIVE → 签发会话 → 清当前手机号计数 → 返回token。错误验证码增加一次计数，第5次返回429；正常首次计数有600秒TTL，后续失败不刷新。HTTP缺码先被Bean Validation挡住，服务内部缺码分支由单测单独验证。

存储接口的四个方法是 `findFailureCount`、`consumeCode`、`incrementFailureCount`、`clearFailureCount`。它们不是一个事务：验证码已消费后SQL失败，Redis不会自动还原；会话已签发后清计数失败，也不会自动撤销会话。

## 不能从“用了Lua”推导出什么

原计数Lua的INCR成功、EXPIRE失败会留下无TTL计数。脚本异常不会回滚已执行命令，下一次INCR变成2也不会再执行首次EXPIRE。7AG迁移原脚本，真实故障验收会明确展示这一点；测试手动删除自己制造的故障key再重试，属于夹具恢复，不是产品自动补偿。

真实Redis四个并发消费者只证明同一验证码最多一个成功，不证明整个登录链原子、容量或生产部署效果。组件、HTTP、mock和源码边界检查分别提供不同证据，数量不相加当覆盖率。

试着用40秒解释：为什么服务还需要检查Long/null返回？为什么“会话签发成功”和“登录HTTP成功”可能不同时发生？为什么移动到适配器不会自动修复旧Lua的有效期故障？答案和本轮证据见[阶段记录](../refactor/55-phase-7ag-login-attempt-store.md)。
