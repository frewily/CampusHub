# 作者撤回：隐藏不是删除

实现与证据见[Phase 7K](../refactor/33-phase-7k-post-author-withdrawal.md)。这是AI辅助完成的增量用例，不是本人已独立掌握的证明。

## 为什么用标记而不删行

动态是评论、回复、计数、审核和Feed的父对象。物理删除会丢掉内容、破坏既有读写约束，也难以保留审核解释。本阶段只从可见0变为撤回1，不级联改评论。评论作者仍能独立撤回，管理员仍能处理已有评论并追溯审核；这些动作不恢复动态。

`DELETE /blog/{id}`表示业务撤回，成功只返回空成功。角色允许调用不等于拥有资源：ADMIN也必须是作者本人。先锁保留行、核对作者，再判断重复，所以他人不能靠重复请求绕过归属限制。

## 自动过滤与手写SQL要分开看

Blog上的 `@TableLogic(0,1)` 会影响MyBatis-Plus生成的详情、列表、count和更新条件；不会自动修改XML手写SQL。编辑和新增评论要显式过滤并当前读加锁，而评论自身撤回/隐藏需要保留行锁，审计则直接读独立元数据。这不是“给Entity加一个注解就完成了删除功能”。HTTP接口不直接调用无归属条件的通用deleteById。

## 为何必须用当前读

回复创建先读一级评论可能建立RR快照。如果动态在随后被撤回，沿旧快照再查询可能误判仍可新增；带 `withdrawn=0` 的 `SELECT ... FOR UPDATE` 在动态行锁上等待并复核当前状态。撤回、编辑、评论写入和点赞使用动态先锁的顺序。它们不是乐观版本控制，也不能把Redis一起纳入MySQL事务。

## Feed空页也是一页

Redis批次含两个撤回ID时，不能因为最终列表为空就丢失游标，否则下一请求可能重复读取同批。7K保留原批次minTime/offset，不补齐、不删Feed数据；随后[7L](../refactor/34-phase-7l-follow-feed-cursor.md)修正静态ZSet同分数跨页偏移累计，但成员/分数跨页变化仍可能重复或漏项，不能宣称可靠Feed或冻结快照。单库锁也不阻止此前开始的读取返回旧内容。

## 上线和回退要问什么

先迁移再上新应用；旧应用不识别标记，回退会再次暴露内容。重复DDL只按列名跳过，生产仍需备份和结构核对。图片文件、缓存、审计、数据库原文都保留，撤回不是隐私擦除，不承诺不可恢复删除或生产合规。
