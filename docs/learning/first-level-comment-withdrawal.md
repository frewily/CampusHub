# 一级评论撤回：根可见性与回复生命周期

Phase 7E 补 `DELETE /blog-comments/{commentId}`，仅撤回作者本人的一级评论；与 7D 的 `DELETE /blog-comments/replies/{replyId}` 分开，避免把一级和直接回复的资格混为一谈。两者均复用状态 3（作者撤回），保留原文，不提供恢复或物理删除。

## 资格与权限

路径是正 Java Long；无 body；成功 HTTP 200、`{"success":true}`，不包含 data。USER/MERCHANT/ADMIN 角色可调用，但都只能撤回本人，ADMIN 不覆盖作者，MERCHANT 也不能按商户关系撤回他人内容。目标须 parent_id=answer_id=0、status 为 0/3、所属动态存在。非本人（包括已经撤回）、缺失目标/动态、回复行、不支持的状态/关系统一 404。

普通查询仅用于定位本人评论所属动态，不能用旧快照决定写入。事务先锁动态，再当前读锁评论，同时复核 blog_id、user_id、一级关系和 status。3 不做任何写入直接成功；0→3 与动态 comments 递减同事务，行数不符合预期为 422；方法内部 Mapper 的数据库异常转通用 500，不暴露驱动 cause。写路径与回复创建、7D 撤回保持动态优先锁顺序，不承诺未来任意外部 SQL 无死锁。

## 根撤回为什么不级联修改回复

一级评论属于根作者，下面的回复属于各自作者。根作者撤回根，不等于有权限改写或删除他人的回复。根状态变为 3 后，一级列表排除根；新请求的根下回复读取/创建因为根不可见而返回 404。已有回复行、原文和状态全部保留，不进行级联更新/扣数；回复作者仍能独立调用 7D 撤回自己的符合条件回复，即使父评论已撤回。

这里是“由不可见根遮蔽回复”，不是“所有回复自身已撤回”。例如根+两个正常回复原计数 3，撤回根后聚合为 2，但用户列表不可见这棵树；若一名回复作者再撤回本人回复，聚合为 1。业务不会强迫不属于根作者的内容进入撤回状态。将来做审核、恢复或用户通知时必须分别处理根与回复，不得把当前聚合误当可见数。

已建立只读 REPEATABLE_READ 快照的并发读取可能看到撤回前版本，不保证瞬时屏蔽所有正在执行的请求或跨页快照。撤回后开始的新请求才适用上述可见性；没有前端展示或内容抹除协议。

## 与正在创建回复的事务竞争

创建回复先普通查询可见根，再锁动态和仍可见的根。若撤回事务先获得动态锁并提交，创建回复的当前读无法命中 status=0 根，返回 404、不插入或增加计数；若创建先获得锁，则可以先成功创建，随后根撤回只改变根。不能承诺并发请求全部拒绝，只能按事务实际顺序解释。

真实 MySQL 测试用独立线程调用生产事务服务，在创建的首次可见查询之后完整提交根撤回，再让创建继续，证明当前读拒绝陈旧快照；另验证重复根撤回与新一级评论的 12 参与者混合写入计数。单次可复现竞态和有限并发测试不是持续负载或生产热点性能保证。

## 幂等、计数和迁移边界

正常→撤回只递减根的一次计数；重复看到状态 3 不再扣。NULL/0 下限为零，历史计数和旧关系不重算。匹配行数使用项目默认 Connector/J 语义，与 7D 共用计数 SQL；自定义 useAffectedRows 等连接参数不是本阶段验收范围。回复创建 POST 仍没有幂等键，不能因 DELETE 重复成功而盲目重试创建。

复用现有 TINYINT 状态 3/V007，无新表、索引、V008 或结构迁移；fresh schema 仅说明状态 3 也用于一级评论。已有卷不自动更新注释，已有库仍先具备 V006/V007。回退应用不恢复内容状态或计数，旧 status=0 查询仍排除根；不得自动把 3 改回 0。未来恢复、审核、物理删除、级联、通知、历史修复另定范围。
