# 学习笔记：纯文字校园动态的兼容语义

日期：2026-10-13。本文解释 Phase 7I 已实现的兼容语义；选定本轮验证已完成，具体证据见阶段记录。

## 为什么保留现有图片字段

纯文字发布只需要让“无图片”成为一个有效的校园动态状态。现有 `tb_blog.images` 字符串列可用空字符串表达该状态，因此无需增加帖子类型列、图片集合表或迁移。把归一化结果定为非 null 的 `""`，还能避免依赖数据库 NULL 行为，并让 NON_NULL JSON 序列化保留这个字段。

这不等于图片内容验证：带图片请求仍沿用原有字段行为，本阶段不校验图片 URL、来源或文件是否真实可读，也不改变客户端展示逻辑。客户端看到空字符串时自行显示无图。

## 校验顺序为何重要

无关联门店时，缺失/null/空串/trim 后空白都归一为 `""`；但上限针对原始请求字符串，在归一化前执行。否则把任意长度空白先 trim 后再验，会令大量超长输入绕过 2048 上限。Java `String.trim()` 的语义也应保持明确，不应悄悄换成另一种 Unicode 空白判定。

条件关系必须由 `shopId` 决定：不关联门店允许无图；关联正数门店仍要求非空白 `images`。不能为方便纯文字场景而删除旧关联内容的图片约束。

## 兼容性与证据边界

已有带图校园动态和门店关联动态继续使用原请求形式；发布路径、角色、会话作者来源及旧 Entity 读取保持不变。`images=""` 是字段值，不是 null，因此应被正常序列化。

本阶段不新增路由、数据库结构或迁移；详情、热门、本人、指定作者和 Feed 仍返回旧 Entity。Redis Feed 投递的既有失败窗口、非原子性及点赞数据问题不因纯文字支持而改变。本轮实际通过 71 项定向检查、386 项默认统计（4 设计跳过）、53 项显式 MySQL IT 与 26 组目标 Compose；默认测试不发现 *IT，真实数据库和真实 HTTP/Redis 验证分开执行。不是完整端点、UI、可靠投递或生产性能验收。

## 复述检查

- 无 `shopId`：允许 `images` 缺失/null/空串/trim 后空白，存成 `""`。
- 有正数 `shopId`：`images` 仍须非空白。
- 2048 单元上限检查原始值；超长空白不会因归一化而通过。
- 非空图片原串不改；作者由会话决定；未知客户端字段忽略。
- 条件约束在服务端计算，并以 `@JsonIgnore` 排除客户端同名字段；客户端传 `storeImageValid:true` 不能放行无图片的门店关联动态。
- 回退旧应用不改变数据库或删除已发布行；旧发布接口会重新要求图片，不能宣称仍接受新纯文字请求。
