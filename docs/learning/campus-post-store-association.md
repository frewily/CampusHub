# 校园动态为何不强制关联门店

## 最小业务变化

校园活动、社团见闻并不天然属于某间门店。Phase 7A 保留 Blog/tb_blog 和 POST /blog，把已有 shopId 改成可选关联：省略或 null 表示普通校园动态，提供则必须是正数。不以 0 或虚构的“校园门店”表达无关联，也不新建一套几乎相同的 Post 表。

标题、图片、正文仍必填，长度限制不变；本轮不提供纯文字帖、编辑/删除/审核、评论或通知。正数 shopId 仍是遗留内容关联，不证明作者是商户、不授予门店管理权，当前没有增加门店存在性核验或外键。USER/MERCHANT/ADMIN 都可发布，但匿名和停用账号不能发布。

## 从协议到存储

请求白名单 → BlogCreateRequest（可空 Positive shopId）→ ApiModelMapper → BlogServiceImpl（非空时校验正数，作者取会话）→ BlogMapper → tb_blog。作者、主键和计数仍不能由请求覆盖，计数由模型映射初始化。

旧表的 shop_id 是有符号 BIGINT NOT NULL。V006 保持 BIGINT 和旧关联行，只放宽 NULL，并由 fresh bootstrap 在 V005 后执行。不能只删 DTO 的 NotNull：未迁移的数据库仍会拒绝写入；也不能只改库，因为旧请求校验/服务仍会拒绝空值。

详情/列表/Feed 沿用已有读取。non_null 序列化会省略无关联帖的 shopId，而非保证输出显式 null；客户端不得无条件把 shopId 当正数。保持旧字段和路径不等于旧客户端已经兼容新出现的空关联数据，客户端要另行验证。

## 发布和回退顺序

1. 备份并核对目标库是已审查的结构，先审查/应用 V006；DDL 可能获取元数据锁，MySQL DDL 不参与普通业务事务回滚。
2. 再部署接受可空关联的应用。已有非空卷不会靠重启自动执行 V006；fresh 初始化只用于新卷。
3. 旧应用仍可以向放宽后的库写带门店的动态，但回退到旧代码会恢复发布必须关联门店的要求。
4. 已有无关联动态后，不能直接把字段收紧为 NOT NULL，更不能为回退自动删除动态或填假门店。必须另定数据保留与转换计划；默认保留已放宽的数据库。

脚本在已可空时跳过 ALTER，允许对预期结构重复应用；它不是对任意历史结构、默认值、索引或脏数据的自动修复器。

## 沿用的可靠性边界

当前发布先保存 MySQL，再向关注者的 Redis Feed 投影。Feed 不是内容事实来源。本轮没有增加 outbox/重建机制；Redis 故障仍可能留下已保存但未完整投递的动态，客户端盲重试可能重复发布。不能把正常 fanout 验收当成事务一致、幂等或故障恢复承诺。

## 取舍与面试追问

- 为什么不是 0？NULL 表达关系不存在，0 既不是真门店，也会污染查询/关联含义。
- 为什么不立即改名 Post？持久化和 API 名称是兼容面，先落地真实业务规则，再另定结构迁移。
- 为什么仍要求图片？这是保持现有协议的最小阶段，纯文字发布可以另定规则，不把两个变化捆在一起。
- 如何证明不是只改文档？验证省略/null 的请求、正数旧合同、权限和白名单，再用真实 MySQL/MyBatis验证旧数据/重复迁移与读写，并在目标版本隔离 HTTP/Redis/DB 流程验收。
- 已提供门店 ID 是否可靠？当前只有正数约束，没有存在性/归属绑定保证；不能把用户内容关联当作商户认证。
