# 可靠订单消费：至少一次、恢复与补偿

## 为什么只有 ACK 不够

`XREADGROUP >` 取组里未交付过的新消息，不会自动返回消费者崩溃前已经交付的 pending。`XREADGROUP 0` 也只看当前消费者的历史 pending；换 UUID 名称后不能靠它恢复别人的消息。必须扫描 PEL，按空闲阈值 claim，且不能把恢复入口放在“先发生一次异常”之后。

本阶段选择 Redis 6 的 `XPENDING + XCLAIM`。扫描有游标、有批量上限；游标必须跳过不空闲消息，否则热的第一页会永远遮住后面的旧消息。XCLAIM 再检查 idle，解决扫描快照与接管之间的竞态，但不是数据库执行互斥锁。

## 至少一次不是恰好一次

数据库提交和 Redis ACK 是两个系统的独立操作：提交成功后 ACK 超时，消息会再次被接管。用户锁减少并发，数据库事务负责扣库存与插入一起提交，数据库唯一约束兜底；重复消息以同一订单 ID 命中同一用户/活动的订单后不再扣库存。同业务键但不同 ID 必须核对，不能把“有一条订单”当作原受理 ID 已成功。

owner 检查只能限制旧 worker 的 Redis 状态变更，不能撤回它已经执行的 SQL。claim 太早仍可能重复处理，必须保留数据库幂等与约束。没有实测处理时延时，60000ms 只是保守默认值，不是调优结果。

## 为什么在处理前计数

仅在捕获异常后加次数，会让每次执行到一半就被杀的进程无限逃过上限。在 BEGIN 中持久计数，可以给崩溃也设预算。代价是“数据库其实已提交、ACK 没完成”的消息也可能耗尽预算；因此 DLQ 表示需要核对，不表示可以退款。

固定空闲阈值提供简单有界重试；不是指数退避，批量接管时也可能同时冲击已恢复的依赖。上线要测积压、消息年龄、数据库时延和恢复目标，必要时再设计 jitter/退避，不凭空标高吞吐。

## 归档与补偿的边界

Lua 先检查类型、owner 和计数，追加 DLQ / 建索引，再 ACK 和清计数。Lua 保证不交错执行，不保证运行错误回滚，也不保证断电持久化。归档失败不能 ACK；源消息、PEL、计数、索引、DLQ 的持久化与恢复需要整体设计，不能独立删除 key。

自动返库存最危险的情况是数据库已经提交，但消费者只看到超时。此时返库存会制造额外可售库存。本阶段选择人工核对后的前向补偿：重投原订单 ID，让数据库幂等判断决定是确认已有订单还是继续落单，不改变 Redis 库存、参与集和受理 ID。

同一 DLQ ID 的重复操作返回同一新 Stream ID，避免命令响应丢失后重复补偿；新的失败仍有自己的有限预算。操作 label 和 reason code 留痕，但不能冒充受认证的操作员身份，权限与外部审计仍由运维保障。用户可查的最终订单状态、取消/核销语义属于 Phase 3C。

## 为什么暂不换 MQ

受理库存和 Stream 事件在同一个 Redis Lua 内写入。换成 RabbitMQ/RocketMQ 后，受理成功与 MQ 发布变成新的跨系统双写，不能因为用了专业 MQ 就消失。没有实测瓶颈或独立故障域需求，先补全现有通道的恢复和失败留痕更符合当前范围。升级触发条件、组件成本与运维边界见 ADR 0001。

面试可以解释上述故障窗口与取舍，但不能声称 MySQL 端到端、多实例超卖验证、Redis 持久化恢复或性能压测已经完成。
